代码里重点对照这两条线：

```text
POST → LogController.create → LogStore.insert
     → MySqlLogStore：EntityManager.persist，提交事务
     → MongoLogStore：LogMongoRepository.insert

GET  → LogController.query → LogStore.query
     → JPA条件分页 / MongoRepository条件分页
     → 相同的LogPage响应
```

查询的共同约定是：时间左闭右开 `[from,to)`，按 `createdAt、id` 降序，page从0开始。MongoDB中的 `id` 映射成 `_id`，这里使用字符串ULID。

我们直接使用 `@org.springframework.data.annotation.Id`；老师音频讲的 `@MongoId` 也是Mongo主键映射注解。主键是否自动生成还与字段类型、字段值和映射配置有关。本项目在Controller内明确生成ULID。

每档运行35秒：5秒升压、5秒预热、25秒正式窗口。每个线程最多执行600次；原生吞吐量定时器控制请求节奏，目标为每线程10次/秒。线程数增加后，目标请求率随之增加。循环次数保证运行有界，定时器控制到达节奏。

先看8、16、32线程能否分别稳定达到80、160、320次/秒。再逐级增加，观察实际速率是否跟上目标、响应时间是否变长，以及应用、数据库和发压机的资源变化。

## 第13步：启动MySQL的逐级探索

本机激活已安装依赖的环境，设置本次四台主机地址，SSH口令由终端交互输入：

```bash
read -s 'LAB_SSH_PASSWORD?SSH口令：'
export LAB_SSH_PASSWORD
python scripts/adaptive-experiment.py mysql --prepare --output work/followalong --start 8
```

`--prepare`切换数据库与应用、恢复10万条日志并执行接口验收。每档开始前再次重置数据。控制脚本依据上一档的吞吐和延迟决定下一档；下降超过20%时复测前一档及当前档。观察输出中的 `starting`、`completed`、`diagnosing_drop`、`generator_limit` 等事件。

打开对应目录的 `summary.json`，先读 `threads、target_rps、throughput_rps、p95_ms、error_rate`，再读 `cpu_percent、generator_min_available_mib、healthy_after`。例如 `mysql-read-t384-r2` 表示MySQL、查询、384线程、第2次运行。

## 第14步：发生骤降时按一条线排查

先对比相邻档的原始HPS和延迟，再复测这两档。随后依次查看：

1. `generator-health.txt`：Java进程CPU、RSS、线程数、主机可用内存和健康探测时间。
2. `jmeter.log`、`console.log`：线程创建、内存错误和结束状态。
3. `application.log`、`state-after.json`：HTTP错误、容器重启、OOM和健康状态。
4. `monitoring.json`：同一正式窗口的数据库、应用、发压机CPU和内存。

本次Compiler在576线程出现内存不足，应用健康探测仍返回UP，改用Manager补测后核实发压端影响。补测前在Manager安装相同Java 17与JMeter 5.6.3，将发压堆扩为512 MiB并同步JMX、run-adaptive.sh和jmeter.properties，并保持Prometheus采样。

```bash
python scripts/adaptive-experiment.py mysql --output work/followalong --generator monitor --generator-heap 512 --operation read --start 384 --max-threads 7200
python scripts/adaptive-experiment.py mysql --output work/followalong --generator monitor --generator-heap 512 --operation write --start 256 --max-threads 7200
```

7200为发压机资源保护上限，后续档位仍按实测自适应选择。出现发压端限制时，记录边界；服务端失效需由超时、错误、健康失败或进程状态直接支持。
