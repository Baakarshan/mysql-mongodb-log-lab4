# 每线程一次请求的逐级负载测试

四台服务器分两轮复用数据库与应用，Manager全程使用JMeter 5.6.3发压，Compiler负责构建。主指标为平均响应时间，吞吐量、错误率和分位数作为辅助。

## 发送方式

总线程数分配到5个内置开放式线程组，每组使用even_arrivals持续55秒，每个逻辑线程执行一次请求。5组同时启动，每个线程执行一次读或写HTTP请求。增加总线程数、保持启动时间，就提高了发送强度。总线程数与同时活跃线程数分别记录。

JMeter连接超时2秒、响应超时5秒，HTTP客户端重试关闭。每档恢复10万条种子日志，前30秒预热，正式统计取时钟起点后30–50秒的20个完整秒，最后5秒继续发送以保留边界余量。原生JTL保留全部采样，正式JTL仅含窗口内启动的HTTP请求。

## 指标与发送均匀性

平均响应时间为正式HTTP样本elapsed列的算术平均值，单位ms；另存成功样本平均值。吞吐量为请求数除以20秒，成功吞吐量只计最终成功的请求。失败耗时与错误率一起解读。

逐秒启动数按正式窗口相对起点划分20个完整秒。逐秒HPS偏离窗口均值超过10%、前后各5秒均值之差超过窗口均值的10%，或平均速率偏离计划超过10%时标为发送不均匀；实际HTTP数量少于配置线程数、JMeter异常或实际平均发送率偏离计划超过10%时，标记发送条件不合格。线程名核对每个HTTP线程恰好出现一次。正式窗口对齐UTC整秒，20个分箱均为完整秒。报告保存原生JMeter Hits Per Second截图和从同一JTL计算的逐秒图；原生图自动缩放纵轴时，同时列出实际计数范围。

## 逐级增加与转折诊断

起始总线程数4400。响应仍快且无错时继续增加；平均响应超过基线10倍且达到50ms、错误率超过1%或健康检查失败时，启动细分和诊断。转折附近补充中间档，并复测发送失败的高档。预热阶段中断的运行保留原始记录。本轮将工作线程上限200改为40作对照，连接池保持20，再逐级提高速率。各次重启、数据重置和预热保留记录。

Prometheus每5秒采集整机及逐核CPU、load1、可用内存、I/O等待、磁盘忙碌、JVM堆、GC和活跃线程。MySQL增加Hikari活跃及等待连接，诊断档采集Java线程栈与数据库状态。CPU未满时继续检查局部资源与等待，连接池参数的影响由同档对照及等待指标判断。

## 预试验与正式数据

旧版47次运行按固定速率平台标准重新检查，其中22次不合格。普通线程组Ramp-up的后段补发影响实际发送节奏。修正为JMeter内置Open Model Thread Group的even_arrivals，并将测试树预先裁成单一操作；预热30秒后核验正式20秒平台。计划1620次/秒的预试验实际为1610至1630次/秒。原始JTL、预试验和旧版核验清单均保存。

## 运行与核验

设置LAB_SSH_PASSWORD后执行：

```bash
python scripts/thread-campaign.py --output work/rerun
python scripts/analyze-threads.py work/rerun
python scripts/generate-adaptive-html.py work/rerun --jmeter /实际路径/apache-jmeter-5.6.3/bin/jmeter
```

控制脚本保存RBAC原副本数，暂停共用资源的服务，按MySQL、MongoDB顺序测试，最后恢复副本数。原始JTL使用无损gzip保存，附SHA-256。`analyze-threads.py`核对线程唯一性、平均值、错误数、完整秒HPS及数据库记录增长。

## 内存故障的参数对照

应用机为792 MiB。原配置Tomcat最大工作线程200；出现内存不足与请求退化后，执行`thread-memory-diagnosis.py --output work/rerun`，将最大工作线程设为40。两库保持连接池20、堆256 MiB，从80次/秒开始检查720、1080次/秒附近的响应、发送均匀性与内存，稳定时继续提高；查询在转折附近细分档位。原配置与修正后结果按purpose区分。

查询在1200次/秒出现响应转折后，保持Tomcat最大工作线程40，另做连接池20与40的同档对照；每次重置数据并预热。`scripts/thread-pool-diagnosis.py --output work/rerun`执行连接池40档，并恢复连接池20、以80次/秒检查恢复。结果按purpose区分。
