# 逐级负载与压力转折

四类分别为MySQL读取、MySQL写入、MongoDB读取、MongoDB写入。四台机器分两轮复用数据库与应用，Manager和Compiler按约4:1发送，主指标为平均HTTP响应时间。

## 发送与测量

两台发送机各运行5个JMeter Open Model Thread Group，even_arrivals等间隔到达，每个逻辑线程只发送一次请求。启动前等待5秒，随后发送55秒；前30秒预热，第30至50秒为正式20秒窗口，最后5秒保留边界余量。线程总数N=计划速率×55，同时活跃线程数独立记录。

每档恢复相同的10万条日志。读取固定INFO、UTC 06:00至07:00、第一页20条，匹配2497条；写入使用同一字段规则。读取应用堆192 MiB，写入128 MiB，工作线程40、数据库连接池20。写入连接上限256、接受队列256。读取连接/响应超时均为2秒，写入连接200毫秒、响应500毫秒。两库同一操作采用相同参数。

平均响应为正式JTL中elapsed列的算术平均，包含失败请求；成功均值与错误率另列。固定窗口吞吐量为样本数除以20秒。原生JMeter统计表按样本开始至结束跨度计算吞吐量，与固定窗口值分别解释。

## HPS核验

按请求开始时刻统计正式窗口20个完整秒。以下三项均不超过10%：逐秒HPS相对窗口均值的最大偏差、首尾各5秒均值之差相对窗口均值的比例、平均速率相对计划的偏差。原始预热计数另存，正式平台用于比较。

核对实际HTTP总数、线程名唯一性、JMeter退出状态、发送机每秒可用内存、CPU、线程创建错误及任务配额计数。发送失败的运行保留排查，重测通过后用于性能比较。Compiler发压时停止Docker释放内存，由/proc每秒记录该机资源；其他主机继续由Prometheus采集。

## 从负载转向压力

从80次/秒开始，根据响应和资源逐级提高速率。平均响应超过50毫秒、错误率超过1%或应用健康异常时，细分相邻档位；重新启动后先执行320次/秒55秒调理，再重置数据、预热并独立复核正常端和压力端，最后降回低档验证恢复。探索结果与复核结果分别列出，转折以区间表示。

CPU未满时继续查看逐核CPU、应用连接池、工作线程、监听队列、锁、磁盘等待和GC。内存曲线平稳还需结合最低可用内存和OOM记录。请求超时后服务器可能继续提交，写入记录增长与全部JTL成功数的差值单列。

Prometheus每1秒采集、规则每2秒计算、查询步长2秒。报告展示同类全部档位的应用机蓝色与数据库机橙色CPU、内存，以及Stacked和Unstacked原生图。正式窗口编号对应原始运行目录；独立运行之间包含重置、预热及重启，图中跨越间隙的连接线不表示持续发送。
