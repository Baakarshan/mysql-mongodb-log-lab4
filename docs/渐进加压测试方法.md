# 渐进加压测试方法

读、写分别从低并发开始。每档读取本次响应时间、吞吐量、失败率和压测机资源，再决定下一档；出现吞吐突降时复测原档和前一档，检查请求节奏、应用日志、GC、数据库和压测机资源。

测试计划使用有限循环，设置每档最长运行时间。使用JMeter原生吞吐量定时器，在未饱和时控制请求节奏；加压后实际发送速率、完成速率和响应时间共同反映排队。固定循环次数本身不能保证每秒请求数稳定。

每档升压5秒、预热5秒、正式测量25秒。基线与明显转折、突降和失效档复测，其他探索档测量一次。原始JTL保留全部请求；汇总按请求开始时间提取正式窗口，另列收尾请求。

稳定性统计使用正式窗口内5秒分箱的Hits Per Second及其变异系数，同时给出逐秒数据。相邻档吞吐量下降超过20%时触发诊断；复测是否重现、失败类型和资源变化分别记录。

压力测试继续增大并发，记录响应时间上升、超时、HTTP失败、健康检查失败、进程退出及恢复。压测机达到资源限制时单独标注，不能将压测机故障写成数据库或应用崩溃。MongoDB和MySQL分别从低档探索，结论由实测产生。

Compiler可用内存在高线程运行中降至32 MiB以下时，标记发压端内存限制。为确认骤降来源，使用内存更充足的Manager补测高并发；保持Java 17、JMeter 5.6.3、JMX及应用和数据库参数一致，Prometheus继续采样。汇总按发压机分别计算，两库比较共同完成的有效档位。

Manager在2916线程、256 MiB发压堆下出现Java heap space，扩为512 MiB后继续确认；两库按相同堆上限比较。发压计划35秒，进程退出宽限30秒。

默认线程上限为1800；本次扩堆补测上限设为7200，用于限制发压进程资源。实际探索由观测值决定，达到发压端上限时记录已测范围与限制原因。服务端健康、失败率和响应时间分别呈现。
