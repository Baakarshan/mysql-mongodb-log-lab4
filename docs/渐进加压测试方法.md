# 开放式固定到达率测试方法

四台机器分两轮复用数据库与应用，所有正式发压都在Manager上执行。Compiler负责构建。两库读、写分别从80次/秒开始，依据响应时间、成功吞吐量和错误逐级提高请求到达率。

## 请求怎样发出

`tools/open-load`使用独立调度循环。第n个请求的计划时刻为开始时间+n/速率，不等待前一请求完成。每个到达启动一个轻量HTTP任务；HTTP连接池允许并发建立连接，在途请求随延迟增加。传输层不设置每主机连接数限制，空闲连接复用。

每次测试发起35秒：前10秒预热，随后25秒正式测量；最后等待已发请求完成或超时。总超时5秒，建连超时2秒，发压器不安排应用层重试。读取条件与固定写入正文和两库一致。原始JTL保留全部请求，正式窗口按实际启动时间划分。

发压器的资源预算是384 MiB Go软内存目标、最多12000个在途请求。达到在途上限或调度落后100毫秒时记为漏发，不集中补发欠账。资源预算、漏发和调度延迟均公开；这些设置不改变服务端返回结果。

## 稳定性怎样判断

逐秒记录计划数、启动数、写入socket数、完成数和漏发数。JTL另存每个请求的计划时刻、启动时刻和调度延迟。这里“写入socket”表示客户端已完成发送，服务端实际接受数需结合HTTP指标判断。

目标速率恒定时，先核对实际启动数和写入socket数是否跟上目标，再观察完成速率、P95/P99与错误率。响应变慢时，开放式负载继续启动后续请求；完成速率会受排队和超时影响。图表保留每秒原始计数，不作平滑。

实际启动比例低于98%、正式窗口漏发超过1%、进程异常或主机可用内存低于32 MiB时，标记发压端限制。CPU高占用作为资源证据，与调度延迟和漏发共同判断。发送比例下降时，检查连接超时、端口耗尽和应用状态，判断传输失败发生在哪里；服务端无法接受新连接也会使发送比例下降。

## 怎样逐级加压与排查

低延迟且无错时下一档约加倍；延迟上升时改用约1.5倍。相邻档成功吞吐下降超过20%时，复测前档和本档。错误率达到10%、P95达到3500毫秒或健康检查失败时，复测确认；发压端受限时结束该方向探索。结束后复测峰值档与基线。

出现明显退化后，下一次测试先重启应用、重置10万条初始日志，再预热。确认结果单独列出，不与连续探索结果混写。数据库实际记录增长与JTL成功数并列核对，超时后已提交写入造成的差额保留。

Manager同时运行Prometheus，主机CPU包含监控开销；Prometheus每5秒采集。压测期间临时暂停四项RBAC服务，完成后恢复原副本数。

## 工具与结果

Go发压器直接产生JMeter可读取的标准HTTP列，附加计划时刻和调度延迟。JMeter 5.6.3用于从这些实际样本生成原生HTML，不参与本轮请求调度。HTML展示副本去掉两个附加列，并将时间戳转换为北京时间；gzip原始JTL保持不变。

先用400毫秒慢响应端点验证：每秒启动40次请求，观察同时在途数大于1，确认调度不等待响应。再执行真实两库测试。`verify-open.py`核对请求计数、到达计数、延迟分位数、数据库增长和文件哈希。
