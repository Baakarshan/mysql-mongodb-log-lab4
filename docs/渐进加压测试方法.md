# 每线程一次请求的逐级负载测试

四台服务器分两轮复用数据库与应用，Manager全程使用JMeter 5.6.3发压，Compiler负责构建。主指标为平均响应时间，吞吐量、错误率和分位数作为辅助。

## 发送方式

总线程数分配到5个相同的普通线程组，每组Ramp-up固定35秒，循环次数固定1，按需创建线程。5组同时启动，每个线程执行一次读或写HTTP请求。增加总线程数、保持启动时间，就提高了发送强度。总线程数与同时活跃线程数分别记录。

JMeter连接超时2秒、响应超时5秒，HTTP客户端重试关闭。每档恢复10万条种子日志，前10秒预热，正式统计取时钟起点后10–30秒的20个完整秒，最后5秒继续发送以保留边界余量。原生JTL保留全部采样，正式JTL仅含窗口内启动的HTTP请求。

## 指标与发送均匀性

平均响应时间为正式HTTP样本elapsed列的算术平均值，单位ms；另存成功样本平均值。吞吐量为请求数除以20秒，成功吞吐量只计最终成功的请求。失败耗时与错误率一起解读。

逐秒启动数按正式窗口相对起点划分20个完整秒。最大/最小比达到2或出现零启动秒时标为发送不均匀；实际HTTP数量少于配置线程数、JMeter异常或实际平均发送率偏离计划超过10%时，标记发压限制。线程名核对每个HTTP线程恰好出现一次。JMeter页面的墙钟首尾分箱可能不足一秒，完整秒核验值单独列出。

## 逐级增加与转折诊断

起始总线程数2800。响应仍快且无错时继续增加；平均响应超过基线10倍且达到50ms、错误率超过1%或健康检查失败时，启动细分和诊断。转折前后补一个中间档，复测转折档，再把连接池20改为40作单参数对照。对照后恢复20，检查低负载恢复。各次重启、数据重置和预热保留记录。

Prometheus每5秒采集整机及逐核CPU、load1、可用内存、I/O等待、磁盘忙碌、JVM堆、GC和活跃线程。MySQL增加Hikari活跃及等待连接，诊断档采集Java线程栈与数据库状态。CPU未满时继续检查局部资源与等待，连接池参数的影响由同档对照及等待指标判断。

## 预试验与正式数据

预试验发现提前创建等待线程会触发pthread_create EAGAIN；启用按需创建后，单线程组高档仍出现启动后段补发和积压。正式JMX采用5个标准线程组均分总数，重新执行两库完整序列。原始预试验日志和参数修正保存于evidence/generator-preflight，正式结果使用results/runs。

## 运行与核验

设置LAB_SSH_PASSWORD后执行：

```bash
python scripts/thread-campaign.py --output work/rerun
python scripts/analyze-threads.py work/rerun
python scripts/generate-adaptive-html.py work/rerun --jmeter /实际路径/apache-jmeter-5.6.3/bin/jmeter
```

控制脚本保存RBAC原副本数，暂停共用资源的服务，按MySQL、MongoDB顺序测试，最后恢复副本数。原始JTL使用无损gzip保存，附SHA-256。`analyze-threads.py`核对线程唯一性、平均值、错误数、完整秒HPS及数据库记录增长。

## 内存故障的参数对照

应用机为792 MiB。原配置Tomcat最大工作线程200；出现内存不足与请求退化后，执行`thread-memory-diagnosis.py --output work/rerun`，将最大工作线程设为40。两库保持连接池20、堆256 MiB，分别检查80、720、1080次/秒附近的响应、发送均匀性与内存。原配置与修正后结果按purpose区分。
